# Agent Note: Novel-writing mode as a shipped preset plus a reading panel

Status: implemented

English | [中文](2026-08-30-novel-writing-mode-shipped-preset-and-reading-panel.zh.md)

## Problem

The harness ships agent presets (per [per-session agent presets](../architecture/2026-08-03-per-session-agent-presets.md)), but every shipped preset composes the same engineering loop: shell, filesystem, planning, delegation. Writing long fiction is a different loop — the working artifacts are manuscripts and ledgers, not code, and the author reads them outside the transcript. The ask was a novel-writing mode that works on a fresh machine with nothing but the repository: clone, `pnpm install`, `pnpm dsh web`, and the mode exists with its craft skills, its tools, and a way to read the novel.

Three design questions had no shipped answer:

1. Where do mode-specific model tools live when they belong to one preset only?
2. How does a browser surface read a session's manuscript without a new transport seam?
3. What holds the writing state — chapter statuses, the foreshadow ledger — so the panel and the tools never disagree?

## Decision

**The mode is one shipped preset plus one client package, nothing else.** `packages/preset/agent-presets/presets/novelist/` composes the writing loop: persona, thirteen craft skills loaded from the preset's own `skills/` directory via the `customSkillDirs` `!!js baseUrl` pattern, the planning group dropped (plan-mode semantics are an engineering loop), and a delegation group kept for one mode-owned use — the multi-perspective review spawns its four role perspectives in parallel. The skill set covers the full lifecycle: market scan, deconstruction of an existing work, project setup, outline, characters, chapter writing, revision, continuity audit, multi-perspective review, prose de-slopping, manuscript import, short-story writing, and cover briefs. Cross-machine distribution is the repository itself; there is no installer.

**Preset-relative file plugins are the home for preset-only model tools.** `plugins/novel-tools.js` sits inside the preset directory and is referenced as a relative row (`./plugins/novel-tools.js`). Because a preset directory ships no `node_modules`, the file imports zero npm packages — Node builtins arrive through `process.getBuiltinModule`, and the only services are the injected `tools` registry and `ctx.fs`. Tool paths resolve against the calling agent's session workspace (`exec.agent?.session.header.cwd`, the same rule `dsh-tool-fs` follows), never `process.cwd()`, and file operations go through `ctx.fs` so a sandboxing backend keeps enforcing its policy. This is the pattern any future preset-scoped tool should copy; the `customSkillDirs` trick and this row form one convention.

**Writing state lives in one durable ledger the tools own.** `.novel/board.json` is the single source of truth, mutated only by `novel_board_read` / `novel_board_update` / `novel_track` with a version-guarded write. Beyond chapter statuses and the foreshadow ledger (ids `F01`…, statuses 已埋/已推进/已回收, importance, planned payoff) the board carries the tracking protocol: character snapshots (identity, location, goal, state, abilities, relationships, knowledge, open threads), the dual timeline (author-truth events with reader-visible reveal status; the reader view never shows an unrevealed event), per-chapter records, and a seven-part context card (position, long-term constraints, active characters, continuity risks, recent chapters, next-chapter commitments). A transactional `novel_track commit` re-reads the chapter file, measures visible characters (`novel_wordcount`'s metric), enforces word bands (±12% internal, ±15% user; out-of-band commits need the author's explicit `acceptCurrentLength`), bumps `stateRevision`, and regenerates every derived view under `.novel/` — which are tool-owned and never hand-edited; `novel_track check` compares rendered content and a revision transaction heals manual edits. Author memory (`.story/author-memory.json`, kinds prose_style/story_design/workflow) survives across sessions through `novel_memory` with a record→receipt contract. `outline.md` is the human-edited companion, and the skills fix the reconciliation rule: when they disagree, the board wins. The reading side (`packages/client/ui-novel/src/board.ts`) re-derives chapter rows by joining `chapters/*.md` word counts with board statuses and degrades unknown board shapes to defaults rather than failing the panel — the board is durable file content that authors hand-edit.

**The panel reads over two webserver routes, not a new transport.** The node half of `@deepseek-ai/dsh-client-ui-novel` registers `/novel/overview` and `/novel/document` as read-only exact routes resolving the workspace through `ctx.sessions.get(id)?.header.cwd`; the webserver is an optional read, because a transport-less boot (headless, CLI test harnesses) must still mount the panel entry without routes. `/novel/document` serves one sanitized workspace-relative `.md` file (no traversal, no non-`.md`, 200 KiB cap) so the same endpoint covers chapters, the outline, character sheets, and the tool-generated tracking views (context card, character snapshots, foreshadow table, dual timeline, per-chapter records), which the panel lists under a tracking tab. The browser half seats a `conversation.view` entry named `novel` through `slots.inject` — the contribution follows the slot's declaration — and holds no store: one overview fetch on mount, one document fetch per opened row, manual refresh because the panel deliberately does not subscribe to file events.

**A client package with a real node half splits its compiler faces.** ui-novel is the first feature plugin whose `src/index.ts` does real work (route registration over `webserver`/`sessions`/`fs`), so the single `tsconfig.base.client.json` leaf broke down: the node files import `node:http` and host services the client program must not compile. Following the `client/connection` precedent, the package now carries `tsconfig.host.json` and `tsconfig.client.json` leaves (host: `board`/`routes`/`index`/`invariant`; client: `board`/`client/**`) plus a solution-only root, with the aggregates referencing the leaves directly. `board.ts` is the shared file and is deliberately browser-safe — truncation uses `TextEncoder` byte-walking, not `Buffer`. This is the worked example for the next feature plugin that grows a node half.

## Alternatives considered

**A standalone `novel-kit` directory with an installer.** The first plan shipped the preset and panel as an out-of-repo kit with an `install.sh` and a custom npm scope. It lost to repository integration on every axis the user cared about: `pnpm install && pnpm dsh web` then auto-loads everything, upgrades ride `git pull`, and the repo gates (constraints, typecheck, coverage, doc-sync) hold the new code to the same bar. The custom scope (`@winterhuan`) is impossible in-repo anyway — the workspace gates hardcode the `@deepseek-ai/dsh-` prefix — so the kit variant only added an installer without buying independence.

**A shared board-schema package.** Exporting the board normalization from an npm package and importing it from both the preset file and the client package would keep one copy of the shape. Rejected: the preset-relative plugin cannot import npm packages at all, so the shared package would serve only the TypeScript side and the preset file would keep its own copy — two homes either way, now with a dependency edge between them. The shape contract is small, versioned through `formatVersion`, and enforced by tests on both sides.

**A deliverables-style transcript surface instead of a view.** Rendering chapters as Chat nodes would put manuscript text into the session log and couple reading to the transcript window. Rejected: the manuscript already lives in files; a view over the workspace reads any chapter instantly, costs nothing in the session log, and keeps the KV-cache story empty (the panel adds no model-visible content).

**Event-driven panel refresh.** Subscribing the view to `tool/result` events to refresh after every agent write would make the panel feel live but couples it to tool vocabulary it does not own and re-renders on every unrelated tool call. The manual 刷新 plus remount covers the reading flow; revisit only if authors report staleness as a real friction.

## Consequences

The writing mode's state model is now a contract three parties rely on: the preset tools write `.novel/board.json` under a version guard, the panel's `src/board.ts` reads it shape-tolerantly (and shares the visible-character metric), and the skills pin the reconciliation rule (board wins over `outline.md`). Any schema change must move all three plus `formatVersion` in one PR. The preset-relative plugin convention (zero npm imports, `process.getBuiltinModule`, session-cwd resolution, `ctx.fs` for mutations) is the template the next preset-scoped tool copies, and ui-novel's split-face tsconfig is the worked example for the next feature plugin that grows a node half — the "ordinary two-entry client plugins do not split" rule now has a second, documented exception shape beside `client/connection`. The panel adds no model-visible content, so the mode's token and KV-cache story stays exactly its persona and skills; everything an author sees outside the transcript rides the two read-only routes, which resolves to zero new transport seams. The cost accepted: the board shape exists twice by necessity, held compatible by tests and the shared `formatVersion`, and the panel's freshness is manual by design until file-event subscription earns its complexity.

One existing consumer of composition files needed its contract clarified in the same change: the webworker packer's roster scan read any row `name` containing a `/` as a package specifier, so the preset's relative file row `./plugins/novel-tools.js` entered the packed dependency closure as the unresolvable name `.`; the scan now leaves preset-relative rows to their own preset directory (enforced by a packer test), which is the standing rule for every future preset that ships file tools.
