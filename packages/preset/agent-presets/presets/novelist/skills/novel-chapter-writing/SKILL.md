# 写作：单章流程与一致性纪律

一章是完整的工程单元：有目标、有产出、有状态回写。不要「先随便写写」。

## 1. 动笔前（核对，不跳过）

1. `novel_track`（action: check）通过后读 `.novel/上下文.md`：当前位置、长期约束、核心角色状态、活跃伏笔、下一章承诺、连贯性风险。
2. 重读 `outline.md` 中本章细纲（阶段位置、结构公式、禁止提前释放、结尾钩子）与相邻两章——本章是承上启下的，不是孤立的。
3. 重读本章出场人物的 `characters/` 小传（至少「语言指纹」与「设定事实」区）；久别复用角色加读 `.novel/角色状态/<名字>.md` 动态快照。
4. 用 `fs-search` 在已有章节中检索本章涉及的专有名词/设定，确认事实写法（人名写法、能力边界、时间点）。

## 2. 本节速记（状态筛选）

写正文前，把已加载的上下文压缩成一张速记卡，只保留「不知道就会写错」的信息，其余留在文件里：

- **角色状态**：本章出场角色的当前身份、位置、目标、最近一次关系变化。
- **历史因果**：本章要回收/推进的伏笔——埋设细节、埋设章节、前文铺垫句。
- **世界约束**：本章涉及的能力边界、组织流程、地理/时间规则。

判断方法：本章细纲提到的角色 → 保留其当前状态；本章有伏笔回收 → 保留埋设细节与铺垫；涉及特定地点/能力/规则 → 保留约束；纯背景知识（与本章无因果关联）→ 丢弃。速记卡是本章的热上下文，不是全部上下文。

## 3. 场景清单（写在正文前）

把本章拆成 2–4 个场景，每个场景一行：

- 地点 + 时间线位置（距上一章多久）
- 在场人物 + 各自当下想要什么
- 场景出口（信息变化 / 关系变化 / 局势变化，至少占其一）

没有出口的场景删除。两个场景出口相同则合并。

## 4. 模块召回四问

动笔前口头回答，答不出先回读材料再动笔：

1. 本章交付什么情绪？（低压章答「关系/信息」也算，但必须答得出）
2. 用哪个已验证模块？（对标书的情绪模块、节奏参考或题材卡，写明来源）
3. 技法落在哪些段落？
4. 爽点出手前，可指认的危机/期待铺垫是哪一段？装逼/打脸/揭露章：在场配角的差异化反应安排了吗？

没有可指认铺垫的爽点不写，先回细纲补铺垫情节点。

## 5. 初稿纪律

- 顺着场景清单写，先完成再修饰；卡住的场景写「【待补：×】」标记后跳过，不停笔。
- 对话遵守语言指纹；叙述遵守视角纪律（`AGENTS.md`）。
- 章尾必须有钩子：未决的威胁 / 新信息 / 关系变化。纯情绪收尾不算钩子。
- 新专有名词当场进 `AGENTS.md` 命名表；新伏笔当场进事务的 foreshadowChanges。
- 细纲优先：只展开细纲已有事件，把每个情节点演成场景，不照抄概括语，也不逐句复述细纲措辞。

## 6. 字数带与 novel_wordcount checkpoint

- **双带**：内带 ±12%，用户带 ±15%；作者本轮明确给出上下限时，原样范围优先于自动比例带。
- `novel_wordcount`（输入 `{file, target}`）是纯测量：返回 actual、双带判定与剩余用户区间，不改正文、不做语义判断。**每章最多调用一次**（checkpoint 语义）。
- **两段式**：把本章情节点按叙事顺序分成连续两组 → 先写前组到临时文件 → 对前组调一次 `novel_wordcount` 得 actual 与剩余区间 → 只用剩余情节点写后组，不得为字数新增独立事件、人物决定、关系变化、揭示或支线 → 剩余情节点写完即停，组装成 `chapters/NN-章名.md`。
- **带外处置**：欠长不加剧情不注水；超长最多做一次净删（删解释与重复，不删情节点/钩子/伏笔），删完复测；仍带外交作者裁决——接受当前长度（commit 时 acceptCurrentLength=true）、调整字数目标，或放弃本稿。不做逐点配额、字数重试或落盘后扩写。

## 7. 写后收口

正文落盘不是汇报时机。同轮内完成三件事，再向作者汇报：

1. **元信息扫描**：标题行以外的正文不得出现写作工程词——「第X章」「上一章」「本章」「前文」「后文」「伏笔」「细纲」「读者」。需要承接前文时，改成角色能感知的事件锚点或相对时间（「比第一章那三秒开火更疼」→「比那三秒开火更疼」）。例外：角色在故事世界内真实阅读/讨论章节文本，或真实身为作者/读者并谈论读者身份。
2. **禁用词扫描**：对照 novel-deslop 的最毒句式速查与一级禁用词表逐处检查（「不是A而是B」「，带着…」「眼中闪过一丝…」「深吸一口气」等），命中即改；改完通读一遍，防止删出电报体。
3. **重读钩子与爽点**：章尾有往下看的理由；高压/推进章爽点前有铺垫、在场配角有差异反应。不达标只修细纲已批准的内容，不借修复补新剧情。

## 8. 追踪提交与回写（一章完成的定义）

1. 构造逐章事务：`novel_track`（action: commit, mode: append）——chapter、chapterTitle、expectedRevision（取 check 返回的 stateRevision；状态已变则重读重构）、delta{result、characterChanges、foreshadowChanges、timelineChanges}、context{position、longTermConstraints、activeCharacters、continuityRisks}、核心复用角色附 characterSnapshots、wordTarget；带外被接受时加 acceptCurrentLength=true。只记录影响未来章节的变化；过程日志、质检计数不进事务。
2. 提交成功后 stateRevision+1，全部派生视图由工具重建——禁止手改 `.novel/` 下任何派生文件；派生文件缺失或 check 报不一致时，重跑产生该状态的完整事务修复，不手写快照。
3. `outline.md` 勾掉该章并核对 exit 是否与正文一致——不一致以正文为准，回头改大纲。
4. 本章首次引入复用角色/组织时，补 `characters/` 小传与 `AGENTS.md` 命名表。
5. 向作者报告：本章字数、exit 达成情况、埋设/推进/回收的伏笔、下一章的 enter。

## 9. 连续性红线

写正文时禁止凭记忆回答以下问题，必须检索既往章节：某角色现在知道什么、某物在哪、某事件发生在第几章、两地距离/时差。记忆会漂移，文件不会。
